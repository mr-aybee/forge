This guide installs RustFS on one node, or across several for high availability, so that Forge runs it as a
managed S3-compatible object store. For how stores, members and credentials
fit together, see [Object storage](/docs/concepts/object-storage/). If the node
already runs RustFS from the App Store, you can
[adopt that container](/docs/guides/adopt-app-store-rustfs/) instead of installing
a new store.

## Before you begin

- You need the `storage.manage` action on the node: role **Operator**,
  **Admin** or **Platform admin**.
- `storage.manage` requires an MFA-verified session. If yours is not, Forge
  asks for an authenticator code (step-up). See [MFA](/docs/guides/mfa/).
- The node is enrolled and online. See [Add nodes](/docs/guides/add-nodes/).
- The control plane can reach the node on the S3 port (default `9000`). S3
  calls run from `forge-server`, not from the agent.
- The S3 port and the optional console port are free on the node and are 1024
  or higher.
- If the data lives on its own volume, mount it first, for example at
  `/srv/objstore/media`.
- To assign the store to an environment, you also need the `deploy` action on
  that environment: role **Developer**, **Operator**, **Admin** or
  **Platform admin**.

<Tabs>
<TabItem label="Linux">

Debian/Ubuntu and RHEL-likes, `x86_64` and `aarch64`.

- **Native** runtime: `curl` and `sha256sum` on the node, and outbound HTTPS
  to GitHub for the RustFS release.
- **Docker** runtime: Docker Engine on the node (App Store **Docker Engine**)
  and access to the `rustfs/rustfs` image.

</TabItem>
<TabItem label="Windows">

Native runtime only, `x86_64` only. RustFS runs as a `SYSTEM` scheduled task
named `forge-objstore-<slug>` that starts at boot and restarts on failure.
Forge adds firewall rules named `forge-objstore-<slug>-<port>`. The Docker
runtime is not supported on Windows.

:::caution
Windows support is implemented but not yet validated in the test lab. Try it
on a non-production node first.
:::

</TabItem>
</Tabs>

## Install a standalone store

1. Open **Object Storage** and select **Install RustFS**. Choose the topology
   **Standalone** (one node) and select **Next**. For a highly available store,
   see [Install a distributed (HA) store](#install-a-distributed-ha-store).
2. Enter a **Name** for the store. The **Instance name** (slug) defaults from it, for example
   `media`. The slug must match `[a-z][a-z0-9-]{0,30}` and be unique on the
   node.
3. Select the **Node**. Offline nodes are listed but disabled. Windows nodes must be x86_64.
4. Choose the **Runtime**: **Native** (release binary as a system service) or
   **Docker** (container, Linux only). For a Windows node the console fixes it to **Native**.
   Forge checks Docker on the node first. When Docker is not installed, cannot
   be reached or the OS is not supported, **Docker** cannot be chosen and the
   reason is shown.
5. Enter the **Release**: `latest` or an exact RustFS release such as `1.0.5`.
6. Enter the **Data path**, for example `/srv/objstore/media` or
   `D:\objstore\media`. No other store may use it.
7. Turn on **Require a dedicated mount** if the data path is a separate
   volume. Forge then refuses to install or start the store while the volume
   is not mounted.
8. Set the **S3 port** (default `9000`) and, if you want the RustFS console, a **Console port**. Set an **Endpoint host**
   if the control plane reaches the node by
   another name or address than its hostname. Change the **Region** (default
   `us-east-1`) if your S3 clients sign for another region.
   For the **Docker** runtime, optionally set the container options: image,
   container name, restart policy, network, memory and CPU limits, extra
   RustFS variables, and per data path a host directory or a Docker named
   volume. See [Docker settings](/docs/reference/rest-api/#docker-settings)
   for every option and the variables you may set.
9. Optional: in **Environment**, choose the environment the store belongs to.
   Leave it on **Shared (no environment)** for a shared store. See
   [Assign a store to an environment](#assign-a-store-to-an-environment) for
   what this changes.
10. Select **Review**, check the node, data path, ports and runtime, then select
    **Install**. Forge creates a root credential in the vault and starts a
    `storage.action` job. The dialog shows the job steps and live output.

The same request through the API:

```http
POST /api/v1/object-stores
{"name": "Media", "slug": "media", "runtime": "native", "server_id": "<server-id>",
 "data_path": "/srv/objstore/media", "require_mount": true, "s3_port": 9000}
```

Add `"environment_id": "<environment-id>"` to assign the store to an environment.
The response is `202` with the store and its jobs. Add `"region"` and a
`"docker"` object for the region and container options.

:::note
Forge never deletes a Docker named volume, also not with **Delete data**.
Remove it yourself with `docker volume rm <name>` when you no longer need it.
:::

## Install a distributed (HA) store

A distributed store is one RustFS erasure-coded cluster across several nodes.
It keeps serving data when drives or nodes fail, within its parity. See
[Standalone and distributed](/docs/concepts/object-storage/#standalone-and-distributed)
for how it works and what counts as a failure domain.

### Before you begin

- Everything in [Before you begin](#before-you-begin), on every node.
- At least 2 Linux nodes, at most 32. Windows nodes cannot join.
- The same number of drives (data paths) on every node, at least 4 drives in
  total, at most 16 per node and 64 in total. Fewer than 4 drives is refused
  in the wizard and by the API.
- The **node** is the failure unit. Several drives of one node may share a
  disk; Forge allows that and notes it in the job log. Drives of different
  nodes on one NAS fail together, so avoid that.
- Every node resolves and reaches every other node on its endpoint host and
  the S3 port. The members replicate over that port, so open it between them.
- The same release on every node. Forge installs one release for the store.
- For the **Docker** runtime, Docker Engine on every node. Distributed
  containers use the host network, so the S3 port must be free on the host.

### Steps

1. Open **Object Storage**, select **Install RustFS**, choose the topology
   **Distributed (HA)** and select **Next**.
2. Enter the **Name**, **Instance name**, **Release**, **Runtime**, **S3 port**
   and optional **Console port**. The ports are the same on every node.
3. Under **Nodes and drives**, set **Drives per node**.
4. For each node, choose the **Node**, set its **Endpoint host** if the other
   nodes reach it by another name than its hostname, and enter one data path
   per drive. Select **Add node** for more nodes. The counter shows the total
   drives against the minimum of 4.
5. Turn on **Require a dedicated mount** if each drive is a separate volume.
6. Optional: in **Environment**, choose the environment the store belongs to.
   Leave it on **Shared (no environment)** for a shared store.
7. Select **Review**, check the nodes, drives and endpoints, then select
   **Install**. Forge starts one `storage.action` job per node. They run in
   parallel, and each node waits up to 15 minutes for the others before it
   reports healthy. While a node waits, its job output says every 30 seconds
   which members have not answered yet.

### Drives that share a disk

RustFS protects data across the drives of the whole cluster. Forge treats the
node as the unit that fails: you may put several data paths of one node on
the same disk, for example `/srv/objstore/<store>/disk1` and
`/srv/objstore/<store>/disk2` on the root filesystem of a VM.

When the drives of a node share a device, the node's job log shows a warning
such as `warning: /srv/objstore/<store>/disk2 shares a device with
/srv/objstore/<store>/disk1 on <node>: fault tolerance is per node`. Forge then
sets `RUSTFS_UNSAFE_BYPASS_DISK_CHECK=true` in that member's settings so that
RustFS accepts the layout. The **Review** step cannot see devices on the
nodes, so the warning appears only in the job log.

:::caution
When drives share a disk, losing that disk loses every drive on it at once.
The store survives that only if the parity covers all drives of one node. With
2 nodes of 2 drives each, losing one node's disk takes half the drives:
reads continue, but writes can stop until the node is back. Use 3 or more
nodes, or one disk per drive, for more headroom.
:::

The same request through the API:

```http
POST /api/v1/object-stores
{"name": "Media HA", "slug": "media-ha", "topology": "distributed", "runtime": "native", "s3_port": 9000,
 "members": [
   {"server_id": "<server-id-1>", "endpoint_host": "<node-1-host>", "data_paths": ["/srv/objstore/d1", "/srv/objstore/d2"]},
   {"server_id": "<server-id-2>", "endpoint_host": "<node-2-host>", "data_paths": ["/srv/objstore/d1", "/srv/objstore/d2"]}
 ]}
```

:::note
Forge's own bucket and object calls use the first member that accepts a
connection. Forge does not yet create a load balancer or DNS name for your
services; put one in front of the members yourself. A standalone store
cannot be converted to distributed, and adding nodes later is not supported
yet.
:::

## Verify

- The store shows status `running` on **Object Storage**. For a distributed
  store, every member on the store page shows `running`.
- For a distributed store, each node's job log ends with
  `RustFS <slug> answers on port <port>`.
- **Test connection** on the store page reports the latency and bucket count.
- On a Linux native install, `systemctl status forge-objstore-<slug>` shows
  the unit active. For Docker, run `docker ps --filter name=forge-objstore-<slug>`.
- On the node, `curl -fsS http://127.0.0.1:9000/health` succeeds.

## Operate the store

The store page lists each member node with its **Data path**, mount state
(**dedicated** or **shared disk**), free and total capacity, and status. Its
buttons start `storage.action` jobs and open the job log:

| Button | Effect |
| --- | --- |
| **Start**, **Stop**, **Restart** | Controls the service. **Stop** and **Restart** ask for confirmation because S3 clients lose access. |
| **Refresh status** | Checks the service, health endpoint and capacity on the node. |
| **Repair** | Runs the install again for the requested release. Data and the root credential are kept. Disabled for an [adopted](/docs/guides/adopt-app-store-rustfs/) store. |
| **Settings** | Changes the release, ports, region and container options. See [Change object store settings](/docs/guides/object-store-settings/). |
| **Uninstall** | Removes the service and firewall rules. |

:::caution
**Uninstall** on the store page never deletes the data path, and the root
credential stays in the vault for recovery. Apps that use the endpoint lose
access. To delete the data too, use **Remove…** in the list (see below).
:::

## Disable, enable or remove a store from the list

Each row on **Object Storage** has a **⋯** menu. Right-click a row for the
same menu. You need `storage.manage` on the store's node, which requires an
MFA-verified session.

| Action | Effect |
| --- | --- |
| **Disable** | Stops the store on every node. Data, settings and the credential stay. The status becomes `disabled`, and status checks keep it so. |
| **Enable** | Starts a disabled store again on every node. |
| **Remove…** | Uninstalls the store on every node, one job per node. Works for `failed` and `error` stores too. Choose **Keep data** or **Delete data**. |
| **Disconnect** | Connected stores only. Forge forgets the connection and its credential. The provider's data is untouched. |

To remove a store:

1. Open **Object Storage**. Turn on **Show disabled and failed** if the store
   is hidden.
2. Open the row's **⋯** menu and select **Remove…**.
3. Select **Keep data** or **Delete data**. For **Delete data**, type the
   store's name. Forge asks for a step-up if your session is not MFA-verified.
4. Select **Remove**. Follow each node's job in **Jobs**.

From the command line, `forge storage action <store> uninstall` keeps the
data and `forge storage action <store> uninstall --delete-data` deletes it;
see [`forge storage action`](/docs/reference/cli/storage/#forge-storage-action).

The store leaves the list when every node reports it removed. A node that is
deleted or revoked cannot run anything, so its member is dropped and the API
response lists it under `skipped`.

:::caution
**Delete data** removes every file in the store's data paths on every node.
A data path that is its own mount point stays as an empty directory. This
cannot be undone.
:::

### What delete data never touches

Forge writes an ownership marker, `.forge-objstore`, holding the store id into
each data path. It writes the marker at install and adopt, and on the next
status check for stores installed before markers existed. It claims only an
empty directory or one that already holds RustFS data (`.rustfs.sys`). A
directory with other files is never marked, and the job log says so.

**Delete data** removes a data path only when all of these hold. Otherwise it
skips that path, keeps going, and logs the reason in the node's job:

| Rule | Log message when it fails |
| --- | --- |
| The path is not a symlink (Windows: not a junction or other reparse point) | `skipped <path>: it is a symlink` |
| No parent directory is a symlink; the path resolves to itself | `skipped <path>: a parent directory is a symlink` |
| `.forge-objstore` exists and holds this store's id | `skipped <path>: not owned by this store` |
| The path is not equal to, inside or around another store's data path on the node | `skipped <path>: it overlaps <other> of another store` |
| No other store's marker lies below it | `skipped <path>: it contains data of another store (<marker>)` |

The service is removed either way. A skipped path keeps its files; delete them
yourself after you check what they are.

:::note
Deleting data needs an agent that knows ownership markers. An older agent
fails the job with `update the agent on <node> to delete data` and removes
nothing on that node. Update the agent, then select **Remove…** again. Other
actions keep working on older agents.
:::

### Default list view

The list shows active stores by default: managed stores that run, are stopped
or busy, and every connected store. Stores that are `failed`, `error`,
`missing`, `disabled` or `removed` are hidden until you turn on **Show disabled
and failed**. The **All**, **Managed** and **Connected** filter and the
checkbox are kept in the URL, for example `/storage?mode=managed&show=all`.

The buttons are disabled while a job runs on the store; hover to see why.

## Assign a store to an environment

A store is **shared** until you assign it to an environment. The roles of
that environment can then see the store and work with its buckets and
objects, and attach its buckets to the environment's services without
`storage.manage`. Managing the store stays with the people who hold
`storage.manage` on its node or workspace. See
[Ownership](/docs/concepts/object-storage/#ownership) for the full rule.

This works for every store: installed, adopted or connected. You need
`storage.manage` on the store (on its node for a managed store, on the
workspace for a connected store) with an MFA-verified session, and `deploy`
on the environment you assign the store to. Clearing the owner needs
`storage.manage` only.

:::caution
Everyone with `view` on the environment then sees the store's endpoint and
the names of its member nodes. **Developer**, **Operator** and **Admin** on
the environment can read, upload and delete objects in **every** bucket of
the store, and can issue a bucket-limited key by attaching a bucket, without
an MFA step-up. Assign a store only when all its buckets belong to that
environment. Keep a store that several environments use shared.
:::

1. Open **Object Storage** and select the store.
2. Select **Change environment** at the top of the store's page. The row
   menu of the store on **Object Storage** has the same action.
3. In **Environment**, choose the environment. To make the store shared
   again, choose **Shared (no environment)**.
4. Select **Save**. Forge asks for a step-up if your session is not
   MFA-verified.
5. If buckets of the store are attached to services of other environments,
   Forge names those services and asks whether to assign the store anyway. Select
   **Assign anyway** only if the new environment may reach those buckets.
   Otherwise select **Cancel** and keep the store shared.

From the command line, use
[`forge storage owner`](/docs/reference/cli/storage/#forge-storage-owner). It
exits with `7` (`attached_elsewhere`) in the case of step 5; add `--force`
to assign the store anyway:

```sh
# Give the store to an environment
forge storage owner <store> --environment <environment>
# Make it a shared store again
forge storage owner <store> --clear
```

The same request through the API. Send `null` to clear the owner:

```sh
curl -sS -b cookies.txt -H "X-CSRF-Token: $CSRF" -H 'Content-Type: application/json' \
  -X PUT https://<forge-host>/api/v1/object-stores/<store-id>/owner \
  -d '{"environment_id": "<environment-id>"}'
```

When buckets of the store are attached to services of other environments,
the request answers `409 attached_elsewhere` and names them. Add
`"force": true` to assign the store anyway.

### Verify the owner

- The store's page shows the owner after **Environment** under its name, or
  **Shared**.
- The **Environment** column on **Object Storage** shows
  `Service / Environment` for the store, or **Shared**.
- Under **Services**, the service's page lists the store under
  **Object stores** for that environment, with its status. A cluster's
  **Services** view shows the same list.
- **Audit** shows `storage.owner.set` with the old and the new owner.

Changing or clearing the owner moves no data and changes no access key.
Buckets that are already attached to services keep working. A store has one
owner; assigning it again replaces the owner. A service cannot own a
store directly, so choose one of its environments.

### Troubleshoot the owner

| Symptom | Cause | Fix |
| --- | --- | --- |
| `404` with `environment not found` | The environment does not exist in this workspace | Check the id with `GET /api/v1/environments` |
| `403` when you assign | You lack `deploy` on the target environment, or `storage.manage` on the store | Ask for the role on both. Clearing the owner needs `storage.manage` only |
| `403 step_up_required` | Your session is not MFA-verified | Enter your authenticator code when asked |
| `409 attached_elsewhere` when you assign | Buckets of the store are attached to services of other environments | Keep the store shared, or detach those buckets first. To assign it anyway, confirm with **Assign anyway** (`"force": true`) |
| `409` with `this environment owns <n> object store(s)` when you delete an environment | The environment still owns a store | Assign each store to another environment or clear its owner, then delete the environment |

## Troubleshooting

| Symptom | Cause | Fix |
| --- | --- | --- |
| Job fails with `port <n> is already in use on this node` | Another service listens on the port | Choose another S3 or console port |
| `409` when you submit | The name, a port or the data path is already used by a store on this node | Pick another slug, port or data path |
| Job fails with `data path … is not a mounted volume` | **Require a dedicated mount** is on and the volume is not mounted | Mount the volume (check `/etc/fstab`), then select **Repair** on the store, or turn the option off |
| Job fails with `checksum mismatch for <asset>` | The download does not match the release's `SHA256SUMS` (corrupt download or a proxy rewriting it) | Retry. If it persists, check proxies between the node and GitHub |
| Status `running`, but the connection test fails with `store_unreachable` | The control plane cannot reach `http://<endpoint-host>:<s3-port>` | Open the port between control plane and node, or set the endpoint host to an address the control plane can reach |
| A distributed member's job output repeats `still waiting after <n> s: no answer from <host>:<port> …` | That member is not installed yet, is still downloading RustFS, or this node cannot reach it on `<endpoint-host>:<s3-port>` (DNS, `/etc/hosts` or a firewall) | Check the named member's own job first. If it is installed, run `curl -I http://<endpoint-host>:<s3-port>/health` from the waiting node and fix name resolution or the firewall, then select **Repair** |
| The job output repeats `still waiting after <n> s: every member accepts connections; the store is starting` and the job fails after 15 minutes with `RustFS <slug> did not answer within 900 s` | The members reach each other but the store does not form. The last RustFS log lines are in the job output | Read the log lines in the job output. Common causes are a data path that already holds data of another store and clocks that differ between the nodes. Fix the cause, then select **Repair** |
| Job fails within a minute with `RustFS keeps stopping on this node (restarted <n> times)` | RustFS exits right after it starts. The last RustFS log lines are in the job output, above the error | Read the log lines, fix what they name (a data path RustFS cannot write, a port in use, an unsupported drive layout), then select **Repair** |
| `400` with `same number of drives` or `at least 4 drives` | The distributed layout is invalid | Give every node the same number of data paths, 4 or more in total |
| Store status `degraded` | Some members are down. Data is served while the failures stay within parity | Select **Refresh status**, then select **Start** or **Repair** on the store (each runs on every member). Losing more drives or nodes stops writes, then reads |
| `403 step_up_required` | Your session is not MFA-verified | Enter your authenticator code when asked |
| The first install fails and the store leaves the list | Forge rolls back a first install that failed on every node: it uninstalls on each node (data paths stay) and deletes the store record and its credential | Open **Jobs**, read the failed `storage.action` job's log, fix the cause and install again |
| A distributed install ran on some nodes and failed on others | The store is kept so that you can see what ran | Fix the failing node and select **Repair**, or select **Remove…** in the row's **⋯** menu |
| Job log shows `warning: … shares a device with …` | Several drives of one node are on one disk | Nothing to fix. See [Drives that share a disk](#drives-that-share-a-disk) |
| A store is missing from the list | It is `failed`, `error` or `disabled`, and hidden by default | Turn on **Show disabled and failed** |
